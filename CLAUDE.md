# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Archery Helper (Bogenampel) — a Flutter app for a target archery club's indoor shooting tunnel, which has two monitors mounted above the shooting line. It implements a shot-clock/traffic-light timer for olympic recurve practice and a competition mode (a WA qualification round), and is meant to grow into a small collection of helper tools for that setup. This is a private hobby project; the author restarted work on it after a longer break (git history goes back further than the recent activity).

The app is built as a desktop-first, keyboard-controlled kiosk display (no mouse/touch interaction expected) — all navigation and timer control flows through `KeyboardConfig`/`AppActionsNotifier`, not widget taps.

## Commands

```bash
flutter pub get              # install dependencies
flutter run -d linux         # run on Linux desktop (or -d windows/macos/chrome)
flutter analyze              # static analysis (flutter_lints via analysis_options.yaml)
flutter test                 # run tests
flutter build linux          # release build; also windows/macos/web as needed
```

Run a single test file with `flutter test test/path/to/file_test.dart`. Widget tests must enlarge the test surface (`tester.view.physicalSize`) — the timer screen's button row overflows the 800x600 default, since the app targets large tunnel monitors. See `test/keyboard_navigation_test.dart`.

## Architecture

State management is **Riverpod** (`flutter_riverpod`), using the newer `Notifier`/`NotifierProvider` API (not `StateNotifier`). The app is bootstrapped in `lib/main.dart` with a manually created `ProviderContainer` so that `settingsProvider` and `keyboardConfigProvider` can be loaded from persistence (`SharedPreferences`) *before* `runApp`, avoiding a flash of default settings.

### Layering

- `lib/models/` — plain immutable data classes (`copyWith`, `toJson`/`fromJson`). No Flutter/Riverpod imports except where enums need `LogicalKeyboardKey` (`keyboard_config.dart`).
- `lib/repositories/` — persistence only, one per model, backed by `shared_preferences` with JSON encoding. Always fall back to defaults on missing/corrupt data rather than throwing.
- `lib/providers/` — Riverpod notifiers holding app state, plus many small derived `Provider`s ("convenience providers") that select a single field out of a bigger state object to minimize widget rebuilds. This pattern is used consistently (`timer_provider.dart`, `settings_provider.dart`, `ui_providers.dart`) — prefer adding a derived provider over watching the whole state object in a widget.
- `lib/core/l10n/` — hand-rolled localization (no `intl`/ARB files). Each screen has its own `*Texts` class (`TimerTexts`, `SettingsTexts`) holding `LocalizedText(de:, en:)` pairs and a `get`/getter API, exposed via a `Provider` that watches `languageProvider` from `settings_provider.dart`. Follow this pattern for new screens rather than introducing `intl`.
- `lib/core/theme/` — the design system. `app_palette.dart` (colour vocabulary), `app_typography.dart` (type scale for distance viewing), `app_dimens.dart` (`AppSpacing`/`AppRadius`/`AppMotion`), `app_theme.dart` (`ThemeData` plus `selectablePanel`, the shared treatment for anything that can hold the keyboard selection) and `timer_theme.dart` (pure functions mapping `TimerState` to signal colour, gradient and text colours), exposed via providers in `lib/providers/ui_providers.dart`. Keep visual logic here, not inline in widgets — widgets ask for a decoration, they do not invent colours.
- `lib/screens/`, `lib/widgets/` — UI. One file per screen (`timer_screen.dart`, `competition_screen.dart`, `settings_screen.dart`, `menu_screen.dart`, `idle_screen.dart`) — `settings_screen.dart` serves all three settings sections, parameterised by `SettingsSection`; `app.dart` only holds `MaterialApp` and `AppNavigator`. Shared widgets: `timer_display.dart` (phase word + clock), `key_hint_rail.dart` (`KeyCap`/`KeyHint`/`KeyHintRail`), `status_chip.dart`. Screens never handle raw key events themselves (see `KeyboardScope` below).

### Central pieces

- **`AppStateNotifier`** (`lib/providers/app_state_provider.dart`) owns which `AppScreen` is shown (`AppNavigator` in `lib/app/app.dart` switches on it) and fullscreen state. This file holds state only — action dispatch lives in `app_actions_provider.dart`, which keeps the dependency one-way and avoids an import cycle.
- **`AppActionsNotifier`** (`lib/providers/app_actions_provider.dart`) is the single dispatch point for all keyboard-driven actions (`AppAction` enum from `keyboard_config.dart`). It handles *global* actions itself (mode cycling, fullscreen) and delegates the *screen-dependent* ones (`navigate*`, `confirm`, `next`, `back`, `resetTimer`) to a **`ScreenActionHandler`**. Note `toggleTimer` (play/pause toggle, bound to `P`) and `next` (context-sensitive advance — start/skip/reset, bound to Space) are deliberately separate actions with different semantics, not duplicates.
- **`ScreenActionHandler`** (same file) has one subclass per `AppScreen`; `screenActionHandlerProvider` picks it via an exhaustive switch, so adding an `AppScreen` forces a decision about its key handling. Add screen-specific key behavior by overriding a method there — never with an `if (screen == ...)` inside `AppActionsNotifier`. Base-class defaults mean "this screen ignores it". Arrow keys arrive as a `NavigationDirection` (not an `AppAction`) so handlers switch over four compiler-checked cases without a `default` clause.
- **`PhaseClock`** (`lib/providers/phase_clock.dart`) is the wall-clock scheduling shared by `TimerNotifier` and `CompetitionNotifier` — a `mixin … on Notifier<T>` with three required hooks (`storedRemaining` as the question to the state, `onRemainingChanged`/`onPhaseElapsed` as the two things that can happen) plus `displayStep`, which defaults to the `showMilliseconds` setting and is only overridden by a clock that needs its own grid. A notifier that follows that setting live calls `watchDisplayStep()` in its `build`. Both clocks are the same rule, so it lives in one place; the paragraph below describes what that rule is and why it is not a poll.
- **`TimerNotifier`** (`lib/providers/timer_provider.dart`) runs the actual countdown off the wall clock: `startTicking` stores an absolute `_phaseEnd` (via `clock.now()` from `package:clock`, so `testWidgets`' fake clock controls it) and every update only *reads* it. A dropped or late callback therefore costs a display update, never countdown time — which is what made the timer lag behind on the web. It does not poll: `_scheduleNextStep` arms a **single** `Timer` for the exact moment the shown number changes (`displayStep` — one second, or 100ms while `showMilliseconds` is on) and re-arms from the clock at each step. Polling on a fixed grid *and* rounding onto that same grid used to let a late callback flip the second up to a step early, so a second was on screen for 0.9s to 1.1s; a timer never fires before its deadline, so the boundary-aligned schedule cannot make that error. The delay is always within `(0, step]` and never longer than the remaining time, which is what keeps a phase exactly as long as it is configured for. Phases move through `TimerPhase` (`idle → preparation → active → ended`). `TimerMode` (indoor/outdoor/custom/alternating) determines default prep/main durations; for `custom` mode, prep/main duration come from `settingsProvider` (`customPrepTime`/`customMainTime`) instead of the enum defaults, and the notifier listens to `settingsProvider` to rebuild its state live when those custom values change. `alternating` is the 1-vs-1 duel: one preparation phase (also `customPrepTime`), then A and B take 20s passages in turn — `_startNextPassage` chains them straight off `onPhaseElapsed`'s `active` case without a new preparation, forwarding the `anchor` so up to six chained passages cannot accumulate drift. `TimerState.hasNextPassage` is the only place that knows the order (A→B→next arrow); the observer's Space key (`advance` → `skipTimerPhase`) drops the rest of a passage and hands over immediately. `TimerMode.defaultWarningThreshold` exists because the shared 30s would make the whole 20s passage amber.
- **`KeyboardConfig`** is a remappable `LogicalKeyboardKey → AppAction` table, persisted like settings; defaults live in `KeyboardConfig.defaults()`. Besides timer/screen actions it also defines `navigateUp/Down/Left/Right` (arrow keys) for in-screen UI navigation.
- **`KeyboardScope`** (`lib/widgets/keyboard_scope.dart`) wraps `AppNavigator` in `app.dart` and is the *only* place raw key events enter the app — every screen is keyboard operable because of it, which matters for a kiosk with no mouse. It re-requests focus on screen changes and forwards `KeyRepeatEvent` so holding an arrow key keeps stepping a value (`AppActionsNotifier._repeatableActions` decides which actions may repeat). Its child is wrapped in `ExcludeFocus`, so no button below can take focus and swallow Space/Enter — the scope structurally keeps the keyboard. Anything pushed as a separate route (dialogs, dropdown overlays) is outside this subtree and needs its own key handling; prefer in-place UI over dialogs for that reason.
- **`SettingsNavigationNotifier`** (`lib/providers/settings_navigation_provider.dart`) owns which settings row is focused (`SettingsItem` enum, in visual order) and translates navigate*/confirm into `settingsProvider` calls. There is no single settings screen: every `SettingsItem` carries the `SettingsSection` it belongs to (`general`/`timer`/`competition`), and stepping only ever walks that section's rows. The open section is not stored anywhere: `openSettingsSectionProvider` derives it from the current `AppScreen`, the notifier **watches** that provider so a section change rebuilds it onto the section's top row, and `SettingsNavState.section` is just `selected.section`. Watching, not `ref.listen`: a listener that assigns `state` fires the moment the new screen first reads the provider — i.e. during the widget build — which Riverpod rejects. The screen therefore does not tell the notifier anything on entry — which is also why the selection is already right in the first frame. `settingsNavigationProvider` and everything derived from it are **`autoDispose`**, and that is load-bearing rather than housekeeping: kept alive, the provider survives leaving the screen, its section goes to `null`, and that pending rebuild is only carried out at the next read — i.e. inside the next settings screen's build, where a changed derived value marks the provider scope dirty mid-build and Flutter throws. Disposed with the screen there is nothing stale to catch up on. The same trap is worth remembering generally: with the manually created `ProviderContainer`, changing state that nothing is listening to defers the whole cascade into whatever build reads it first. Each section has its own reset row, which calls `SettingsNotifier.resetSection` — resetting the Ampel times from the competition screen would be nonsense. `SettingsScreen` only renders that state; mouse interaction selects the row it acts on so both input paths stay in sync. Rows that cannot be used are skipped while stepping (volume while sound is off). Reset uses a two-step inline confirmation (`resetArmed`) instead of a dialog — a modal route would be invisible to `KeyboardScope`, and arming is real state rather than a one-shot event.
- `SettingsScreen(section:)` builds the row list from a switch over its section and each row as its own small `ConsumerWidget` watching a single convenience provider (plus `isSettingsItemSelectedProvider(item)` for the highlight), so a value change or a moved selection rebuilds only the affected rows. Follow that when adding rows; do not watch the whole `settingsProvider` at screen level.
- **`MenuNavigationNotifier`** (`lib/providers/menu_navigation_provider.dart`) is the same pattern for the menu: it owns the focused `MenuItem` (in a `MenuNavState`, like the settings navigation), each item carries the `AppScreen` it opens, and `MenuScreenActions` translates navigate/confirm into it. It holds the four tools (timer, competition, traffic light, idle), the general settings and `MenuItem.quit` — the Ampel and competition settings are deliberately *not* menu entries: they belong to their tool, are opened with S from it and left again with Esc (`SettingsScreenActions._origin` maps the settings screen back to the screen it belongs to). Left/right wrap around the flat order, up/down wrap within the column (the screen reports its column count through `menuColumnsProvider`) — on a keyboard-only kiosk no arrow key may be a dead stop. `MenuItem.quit` is the one entry whose `target` is `null`, i.e. "this is not a screen": it closes the app through `windowServiceProvider` (overridable in tests; `main.dart` still uses the `windowService` constant directly) and, like the settings reset, confirms inline in two steps via `quitArmed` — no dialog, and no key binding at all, so a stray keypress can never black out the display above the shooting line.
- **`CompetitionNotifier`** (`lib/providers/competition_provider.dart`) is the competition mode: a WA qualification round on the same `PhaseClock`, with its own `CompetitionState` rather than more fields on `TimerState`. The rule it encodes: every shooting time is preceded by a preparation phase — at the start of an end the announcement to the first group, afterwards the changeover to the next (`isChangeover` is the only difference, and it only changes the phase word). After the last group of an end the round **stops**: arrows are collected, and how long that takes is not a duration any clock knows, so the state goes back to `TimerPhase.idle` with the next end already set up (`isWaitingBetweenEnds`) and waits for the next start signal — the screen therefore already shows who is up. `idle` means "waiting for the range officer" in both places, which is why there is no extra phase for it. The group order reverses every end (`isOrderReversed` — end 1 AB/CD, end 2 CD/AB), so each group starts equally often. `CompetitionLineup.orderedLabels` is the only place that knows what "reversed" means (the group rail on screen goes through it too, rather than reversing a list of its own), `hasNextGroup`/`hasNextEnd` the only places that know when the round is over. Settings are deliberately few: `CompetitionDiscipline` (indoor/outdoor) carries arrows per end, shooting time and the default end count; only the end count and the `CompetitionLineup` (AB/CD, A/B, all together) are separately settable, and preparation is fixed at 10s. Changing any of the three re-seats the round, like `custom` mode does for the Ampel.
- **`TrafficLightNotifier`** (`lib/providers/traffic_light_provider.dart`) is the traffic light switched by hand: red and green, no clock. Its whole state is a `bool` — deliberately not a `TimerMode`, which is where it used to live: with zero durations it needed a `mode.isManual` exception in six of `TimerNotifier`'s methods, in the theme and in the texts, and none of them earned their keep. It has no `PhaseClock`, and must not get one (with zero durations the schedule would run to `ended` in a single call). Red is `TimerPhase.preparation`, not `idle` — `idle` is tinted at a tenth of the strength and a barely-red screen is not a signal. `trafficLightUIStateProvider` is the only user left of `TimerUIState.showTime`: without a clock the signal word takes its place and is the whole display. Its screen has no settings, nothing to skip and nothing to reset — "back to red" is the toggle — so `TrafficLightScreenActions` returns `ignored` for all three; they still have to be answered, or they would fall through to the base class and reach into the Ampel timer from a screen that does not show it. Space and P both toggle, because without a countdown "further" and "start/pause" are the same act.
- **Two clocks, one set of keys.** Space/P/R/S mean "the clock in front of me", so `toggleTimer`, `skipTimer`, `resetTimer` and `openSettings` are methods on `ScreenActionHandler` (base implementation: the Ampel timer) which `CompetitionScreenActions` overrides. Do not reach for `timerProvider` from a global action again. `SignalState` (`lib/models/signal_state.dart`) plays the same role for the look: both states expose one, and `TimerTheme` maps only that — so the two screens cannot drift apart in colour. `TimerDisplay` takes its `Provider<TimerUIState>` as a parameter for the same reason.
- **Signaltöne** live in `lib/core/audio/` (`AudioSignal` — the vocabulary, named by meaning; `SoundPlayer` — the only place that knows `audioplayers`) plus `signalSoundsProvider` in `lib/providers/sound_provider.dart`, which is the one place that reads `soundEnabled`/`volume`. Both notifiers play their signals from the phase-transition methods themselves (`_startPreparationPhase`/`_startMainPhase`/`_endTimer`, `_startPreparation`/`_startShooting`/`_handOver`) rather than deriving them from state — a transition method is the one place each clock passes exactly once. That is also what keeps `CompetitionNotifier.rewind`/`fastForward` silent: the three tones for arrow retrieval sit in `_handOver`, not in the `_awaitSlot` those two share with it. The Ampel warns in the last 3 seconds (gated on the *displayed* second, since `onRemainingChanged` fires ten times a second in millisecond mode), the competition never does — WA's amber-at-30s is visual only. Multi-tone signals are baked into the WAV file, not sequenced at runtime; `tool/generate_signal_sounds.dart` regenerates `assets/sounds/`, and the files are checked in. Every signal exists in **two voices** (`SignalTone`, `lib/core/audio/signal_tone.dart`) — `assets/sounds/tone1/` is the original pure sine set for the tunnel, `tone2/` the same melody a fifth up with added 2nd/3rd harmonics, which is what makes it carry outdoors (the harmonics land in the 2–4 kHz band the ear is most sensitive to; the generator normalises by the sum of the harmonic weights so the brighter voice cannot clip). The variant is a `_Voice` row in the generator, not a second signal table — `_signals` describes melody and rhythm, a voice transposes it whole. `AudioSignal.fileName` still names the file; only the folder differs, so `AudioPlayersSoundPlayer` keys its player cache on `(SignalTone, AudioSignal)` and preloads both sets. Which one plays is `settings.signalTone`, read in the same one place as `soundEnabled`/`volume` (`SignalSounds.play`), and set from the `signalTone` row in the general settings (skipped alongside volume while sound is off — see `_needsSound`).

### Design constraints that are easy to break

- **No routes.** Dialogs, `DropdownButton` overlays and anything else pushed on the Navigator sit outside `KeyboardScope` and become keyboard-invisible. That is why the settings screen builds its controls (stepper, toggle pill, volume blocks) from plain containers instead of Material's `DropdownButton`/`Switch`/`Slider`, and why reset confirms inline.
- **The signal is the background.** There is no drawn traffic light any more — `TimerTheme.backgroundGradient` tinting the whole screen red/amber/green *is* the signal. Do not reintroduce lamp-like widgets or blur-heavy decoration on the timer screen: the `CustomPainter` lamps with `saveLayer` + `MaskFilter.blur` were the main reason the web build stuttered.
- **No blur anywhere, and selection may not change size.** `lib/` contains no `BoxShadow`, `MaskFilter`, `ImageFilter` or `saveLayer` at all, and that is worth keeping: the selected row used to carry a 32px blurred halo that was lerped onto two large panels on every keyboard step, which is ruinous once the app lands on a software rasteriser (a browser without GPU access does exactly that). The second half of the same rule is subtler — a `Border` is laid out like padding, so a border that thickens on selection relayouts the row *and the whole list* in every frame of the highlight. `AppTheme.selectablePanel(isSelected:)` therefore owns both states and keeps its width private; build selectable surfaces from it rather than assembling a decoration per state. Animate colour, not size.
- **One representation per fact.** The timer screen shows the phase word and the clock, nothing else — the drawn traffic light, the phase progress bar and the "paused" badge were all removed as second copies of what the tint and the phase word already say. Prefer making the existing element bigger over adding another one.
- **Distance readability.** The display hangs several meters above the shooting line: the smallest type in use is 20sp, body copy is 26sp+, and the countdown is scaled by a `FittedBox` rather than given a fixed size. Prefer size and contrast over decoration.
- **No looping animation.** Every animation is a finite implicit one (selection, gradient). Nothing may move while an archer is at full draw — and a repeating controller would also make `pumpAndSettle` hang in tests.
- **Beware per-update rebuilds.** The countdown updates once per shown value — once a second, or ten times a second while `showMilliseconds` is on. Derived providers must still return values that compare equal between updates; a provider that changes on every update repaints the whole tinted screen at that rate *and* makes `pumpAndSettle` in the widget tests run until it times out. Do not reintroduce a polling timer to get finer values: the update rate and the display grid are deliberately the same thing (see `TimerNotifier._scheduleNextStep`), and `formatTime`'s rounding defines the boundary that is scheduled onto.
- **Riverpod schedules its notifications with a `Timer`** when a `ProviderContainer` runs outside a widget tree. Reading a derived provider in a `testWidgets` test after a state change therefore leaves a pending timer that the test framework reports as a leak — assert against the notifier and call `TimerTexts.formatTime` directly instead (see `test/timer_test.dart`).
- `test/ui_layout_test.dart` pumps every screen at 1920x1080, 2560x1440 and 1280x720 and fails on any `RenderFlex` overflow. Note that a `BoxDecoration` border is laid out as padding, so it has to come off the available space before any derived size.

### Conventions to note

- German is the default/primary language (`AppLanguage.german`); English is the secondary, always-present translation. Keep both in sync when adding `LocalizedText` entries.
- Some code comments and identifiers are in German (this mirrors the club/domain context); don't feel obligated to translate existing German comments when editing nearby code.
- `flutter analyze` is expected to be clean (zero issues) — keep it that way rather than letting lint noise accumulate.
